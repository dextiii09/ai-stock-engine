## Critical Bugs Found & Fixed

### 1. [CRITICAL] `NameError` silently blocked every BUY signal in Stocks, Crypto, and Forex markets

**File:** [backend/api/routes.py:1608](backend/api/routes.py#L1608) (`_run_market_loop`, shared by 3 of 5 markets)

```python
if signal == "BUY" and market_name == "CRYPTO" and symbol.upper() == "BTC-USD":
```

`market_name` was never defined anywhere in the ~18,000-line backend (confirmed by a full-repo grep — this was its only occurrence). `_run_market_loop` only receives a `market_label` parameter. Because Python evaluates `and` left-to-right and `signal == "BUY"` is `True` on every BUY signal, this line raised `NameError` **on every single BUY signal** in the Stocks, Crypto, and Forex trading loops. The exception was caught by the loop's outer `except Exception as e: await write_log_fn("error", ...)` handler and logged as a generic per-symbol error — indistinguishable from a transient data-fetch hiccup in the log stream.

**Effect:** these three markets could open a SHORT (via SELL) or close a LONG (via SELL), but could **never** open a new LONG position or cover an existing SHORT, for as long as this code has been live. A "5 simultaneous autonomous markets" system was structurally running at 2/5 (US futures and India, which have their own separate, unaffected loop implementations).

**Fix:** `market_label.upper() == "CRYPTO"` (the loop's actual parameter, compared case-insensitively since `market_label` is passed as `"Crypto"`, `"Stocks"`, `"Forex"`).

**Regression test:** [backend/tests/test_routes_static.py](backend/tests/test_routes_static.py) — `test_run_market_loop_has_no_undefined_market_name`. Since `routes.py` has heavy import-time side effects (FastAPI app + 5 singleton engines + Telegram bot) and is never imported by the existing test suite, this is a static AST check that the identifier `market_name` never reappears in `_run_market_loop`, plus a check that the correct replacement is present. **PASSED.**

### 2. [HIGH] Unvalidated LLM agent voted at permanent full strength in the India market

**File:** [backend/agents/master.py:363-365](backend/agents/master.py#L363), [backend/api/routes.py:1066-1076](backend/api/routes.py#L1066)

`IndianMasterAgent` appends `IndianGeminiAgent` (an agent that calls the NVIDIA NIM / Google Gemini APIs live, `backend/agents/gemini_agent.py`) to its 7-agent committee. The system has an established, explicit principle for exactly this situation: `SentimentAgent` and `CorrelationAgent` are deliberately zeroed (`agent_weights["News & Sentiment AI"] = 0.0`) before every live decision, specifically because they cannot be point-in-time backtested (no historical news archive / lookahead bias) — the code comments call this "System now validates what it deploys," referencing a prior audit fix. `IndianGeminiAgent` has the identical problem — LLM calls cannot be replayed over historical bars — but was never added to that zero-list, and is also absent from the RL engine's tracked agent schema (`_GHOST_AGENTS` in `analytics/rl_engine.py`). Because `master.py`'s weighting is `agent_weights.get(agent.name, 1.0)`, this meant the LLM agent voted with a **permanent, un-learned, un-decaying weight of 1.0** in every India-market decision — the only committee member never subject to either RL tuning or deliberate exclusion.

**Fix:** added `_live_weights_in["Indian Gemini AI"] = 0.0` alongside the existing Sentiment/Correlation zeroing in `indian_trading_loop`, matching the system's own established pattern.

**Regression test:** `test_indian_gemini_agent_weight_is_zeroed` in `test_routes_static.py`. **PASSED.**

**Not fixed / flagged for follow-up:** this only addresses the *India* loop. If `NvidiaMacroAgent`/`IndianGeminiAgent` is ever added to another market's committee, the same gap will reappear there — the RL engine's ghost-agent set would be a more robust place to enforce this once, rather than per-loop zeroing.

### 3. [HIGH] Circuit-breaker halt path crashes on Windows consoles

**File:** [backend/risk/global_risk.py:149](backend/risk/global_risk.py#L149)

```python
print(f"[GlobalRisk] ⛔ {self.halt_reason}")
```

Reproduced directly in this session: on a plain Windows console (cp1252 codepage — the Windows default unless UTF-8 mode is explicitly configured), this raises an unhandled `UnicodeEncodeError`. This is the exact code path that fires when the cross-market circuit breaker halts trading during a drawdown event — i.e. the safety mechanism designed to protect capital could itself crash the entire engine process at the worst possible moment. The repo documents a Windows-native launch flow (`start_web.bat`, `start_trading_bot.bat`) as a first-class supported deployment path, so this is not a theoretical edge case.

This same bug also explained an initially-mysterious test-harness failure in this session: running `pytest backend` crashed at teardown with an unrelated-looking `ValueError: I/O operation on closed file` — caused by this exact `UnicodeEncodeError` corrupting pytest's own stdout-capture layer deep inside a test that exercises the circuit breaker.

**Fix:** rather than patching every emoji-laden `print()`/log call across the codebase (this pattern appears extensively — `🚨`, `✅`, `⛔`, etc.), reconfigured `sys.stdout`/`sys.stderr` to UTF-8 with `errors="replace"` once, at process startup in [backend/main.py](backend/main.py) (production) and in [backend/tests/conftest.py](backend/tests/conftest.py) (test harness).

**Regression tests:** [backend/tests/test_encoding_safety.py](backend/tests/test_encoding_safety.py) — one static check that `main.py` performs the reconfigure before heavy imports, one behavioral check that reproduces the exact halt-message string failing to encode under cp1252 before the fix and succeeding after. **Both PASSED.** The full `pytest backend/tests` suite now completes cleanly with a real summary line (see [Test Results](#test-results)) — previously it could not reliably finish at all on this machine.

### 15. [CRITICAL] Zerodha broker's real-money safety lock had a hole for SHORT and COVER orders

**File:** [backend/execution/broker_zerodha.py](backend/execution/broker_zerodha.py)

`ZerodhaBroker._place_order()` — used by `buy()`/`sell()` — has an explicit, deliberate "Ironclad safety lock": it checks `os.getenv("ENABLE_LIVE_REAL_MONEY_TRADING", "false")` and refuses to place any order unless that flag is explicitly `"true"`, printing `[SAFETY LOCK] Real money trading is disabled...`. This is exactly the kind of defense-in-depth the user's brief asked to verify ("can this create incorrect orders... can software bugs bypass risk controls"). **The hole:** `short()` and `cover()` did not call `_place_order()` at all — they reimplemented order placement inline, calling `self._kite.place_order(...)` directly, with no safety-lock check whatsoever. Compared this against the other two live broker integrations: `UpstoxBroker` and `IBKRBroker` both correctly route **all four** of `buy()`/`sell()`/`short()`/`cover()` through their own safety-locked `_place_order()` — `ZerodhaBroker` was the sole outlier. Concretely: if `broker_config.json` were ever set to `mode: "zerodha"` with valid credentials configured, but `ENABLE_LIVE_REAL_MONEY_TRADING` left unset (its safe default) — the exact scenario the lock exists to protect against — a BUY or SELL signal would be correctly blocked, but a SHORT or COVER signal would place a **real order on the live exchange**. A safety mechanism that silently only covers half of the trade directions is arguably worse than none, since testing BUY/SELL and seeing them blocked would reasonably (and wrongly) build confidence that the broker is fully locked down.

**Fix:** `short()`/`cover()` now route through `_place_order()` (which gained a `product` parameter so the MIS-vs-CNC distinction they need is preserved), matching the pattern already correct in the other two brokers.

**Regression test:** [backend/tests/test_broker_safety_lock.py](backend/tests/test_broker_safety_lock.py) — parametrized across all four order methods, asserts each is blocked with a `"SAFETY LOCK"` message when `ENABLE_LIVE_REAL_MONEY_TRADING` is unset. Does not require the `kiteconnect` package to be installed (the lock check runs before any broker-library usage, by design). **4/4 PASSED.**

### 4. [MEDIUM] Telegram `/system` diagnostics silently claimed "operational" during real failures

**File:** [backend/utils/telegram_bot.py:458-459](backend/utils/telegram_bot.py#L458)

`_get_system_metrics_text()` wraps CPU/RAM/disk collection in a broad `try/except Exception`. On failure (missing `psutil`, permission errors, anything), it returned:

An operator glancing at this during a real outage sees "operational" as the headline and could miss the actual problem, which is truncated to 100 characters in a "Diagnostics:" suffix. **Fix:** rewrote the fallback to `⚠️ Metrics UNAVAILABLE — {error}` (no false "operational" claim), and installed the missing `psutil` dependency so the real metrics path is exercised again.

**Regression test:** `test_system_metrics_failure_is_reported_honestly` in `test_telegram_bot.py`. **PASSED.**

## Security Findings

### 21. [CRITICAL — fixed] TLS certificate validation was disabled in 4 files, including live order placement and OAuth credential exchange

**Files:** [backend/execution/broker_upstox.py](backend/execution/broker_upstox.py), [backend/scripts/auto_upstox_login.py](backend/scripts/auto_upstox_login.py), [backend/utils/telegram_bot.py](backend/utils/telegram_bot.py), [backend/utils/notifier.py](backend/utils/notifier.py)

All four files constructed their `ssl.SSLContext` via `ssl._create_unverified_context()` — which sets `verify_mode=CERT_NONE` and `check_hostname=False`, disabling TLS certificate validation entirely. Confirmed via a repo-wide grep this pattern appears in exactly these 4 files and nowhere else. The severity varies by call site, but two are genuinely serious:

- **`broker_upstox.py`**: the real order-placement HTTP POST to `https://api.upstox.com/v2/order/place` — carrying the live Bearer access token and the actual buy/sell/quantity/instrument payload — is sent over this unverified connection. With certificate validation off, anyone in a position to intercept the network path (compromised Wi-Fi, DNS hijack, a malicious or compromised proxy) could steal the access token, silently alter order parameters in transit, or return a forged success/failure response that desyncs the bot's internal state from what the broker actually did. (Currently `UpstoxBroker.is_live` hardcodes `False` — see below — so this specific call path is not reachable from `SmartExecutionEngine` today, but it fires unconditionally whenever `_place_order()` is invoked directly, e.g. by any future code path or a manual script.)
- **`auto_upstox_login.py`**: the OAuth authorization-code-for-access-token exchange — carrying the real `api_key`/`api_secret`/authorization `code` — uses the same unverified connection, with **no `is_live` gate protecting it at all**. This script is meant to be run standalone (e.g. via cron, per its "Automated" naming) to refresh the live Upstox token; every time it runs, real broker credentials are exposed to interception on the wire.
- **`telegram_bot.py`/`notifier.py`**: every Telegram/Discord alert send and every incoming bot command poll uses the same unverified connection — lower stakes than the broker paths, but still means the two-way remote-control channel (which includes commands like `/halt`) has no real protection against a network-position attacker.

**Why this wasn't a silent, harmless oversight:** the DB-stored broker credentials (`BrokerAccount.access_token` etc.) are properly encrypted at rest via the `EncryptedString` TypeDecorator (confirmed correct in an earlier pass of this audit) — showing the team does take credential protection seriously elsewhere in the codebase. This looks like an isolated gap in the file-based/HTTP-transport paths specifically, not a systemic disregard for security.

**Fix:** replaced `ssl._create_unverified_context()` with `ssl.create_default_context()` (Python's secure default, using the system's certificate trust store) in all 4 files. **Verified this doesn't trade security for broken connectivity**, rather than assuming it's safe: directly tested real TLS handshakes with the new context against `api.telegram.org`, `api.upstox.com`, and `api.kite.trade` in this environment — all three completed successfully with full certificate validation. The original unverified-context choice does not appear to have been a necessary workaround for a broken local CA bundle (a real, common Windows/Python gotcha) — at least not in this environment.

**Regression tests:** [backend/tests/test_tls_verification.py](backend/tests/test_tls_verification.py) — asserts each of the 4 SSL contexts has `verify_mode=CERT_REQUIRED` and `check_hostname=True` (an AST-based check for `auto_upstox_login.py`, which builds its context inline rather than storing it on an object). **4/4 PASSED.**

**Related, lower-severity observation (not fixed — fails safe already):** `UpstoxBroker.is_live` hardcodes `return False` with an explicit `# TODO: Return True only when get_fill_status polling is properly implemented` comment from the original developers. This means selecting "Upstox" as the broker mode is currently completely inert from `SmartExecutionEngine`'s perspective — it silently continues paper-trading regardless. This fails in the *safe* direction (toward paper, not toward real money), so it's not a safety gap, but a user who explicitly selects Upstox in Settings.tsx believing they've gone live would get no indication that nothing actually changed.

### 6. [CRITICAL — flagged, not auto-fixed] Misleading security comment; possible open production API

**File:** [backend/api/auth.py](backend/api/auth.py), [backend/main.py:23](backend/main.py#L23)

- Confirm port 8080 is firewalled/reverse-proxied and not directly internet-reachable, or

I recommend verifying this directly (`curl -X POST http://140.245.210.188:8080/api/v1/risk/emergency-kill-switch` from an outside machine, expecting it to be blocked) before treating this as resolved.

### 17. [LOW] `RiskAgent`'s daily-PnL and max-drawdown vetoes are permanently dead code (redundant, not a live gap)

**File:** [backend/agents/committee.py:606-634](backend/agents/committee.py#L606)

`RiskAgent` (the committee's "final veto" — separate from the 7-agent voting committee, consulted directly by `MasterAgent.evaluate()` at `master.py:220` and confirmed to genuinely block trades when it returns `VETO`, not dead-lettered) reads `data.get("daily_pnl_pct", 0.0)` and `data.get("max_drawdown_pct", 0.0)` and vetoes if either breaches -3%/-8%. ### 18. [LOW — dormant] `rl_engine.load_state()` uses the exact thread/event-loop anti-pattern already diagnosed and fixed elsewhere in this codebase

**File:** [backend/analytics/rl_engine.py:661-695](backend/analytics/rl_engine.py#L661) vs [:551-577](backend/analytics/rl_engine.py#L551)

`smart_execution.py`'s own comments (read in an earlier pass of this audit) document a previously-real bug: spawning a coroutine on a brand-new event loop in a new thread breaks `aiosqlite`, because its connection pool is bound to the *original* running loop — the DB call then fails with `"Queue is bound to a different event loop"`, and the operation silently never completes. That fix (fire-and-forget via `loop.create_task()` on the *same* running loop) is correctly applied in `rl_engine.py`'s own `save_state()` at line 567. But `load_state()`, defined a hundred-odd lines later in the same file, still uses the old, already-disproven pattern for its DB path: when called from within a running event loop, it spins up `threading.Thread(target=run_in_thread)` with a brand-new event loop and blocks on `fut.result()` — exactly the construct the `save_state` fix exists to avoid.

**Why this is dormant, not live:** the only call site is `smart_execution.py:628`, inside `SmartExecutionEngine.__init__()` → `_load_state()`. All 5 `SmartExecutionEngine()` instances (`execution_engine`, `execution_engine_in`, etc.) are constructed as **module-level** statements in `routes.py`, which execute at Python import time — before uvicorn starts the FastAPI app's event loop. At that point `loop.is_running()` is `False`, so the safe synchronous branch (`loop.run_until_complete(coro)`) runs instead, and the broken thread-based branch is never exercised in the current call graph.

**Why it's still worth flagging:** if any future feature calls `rl_engine.load_state()` from within a request handler or background task on the already-running loop — a "reload RL weights from DB" admin endpoint would be a very natural thing to add given the system already has `/models/retrain-all` — it would silently fail to load from the database in exactly the way `smart_execution.py`'s comments describe as already having happened once. **Not fixed**: matching `save_state`'s fire-and-forget pattern isn't obviously correct here either, since `load_state`'s callers currently rely on getting real data back synchronously (the return value matters for a *load*, unlike a *save*) — the right fix depends on whether this method should ever legitimately be called from a running loop at all, which is a design question, not a one-line patch.

### 11. [HIGH] Backtest position sizing does not match live sizing — reported returns/drawdown are not representative of live risk

**File:** [backend/backtesting/engine.py:346,365,547](backend/backtesting/engine.py#L547)

Confirmed by reading the code directly (no `PositionSizer`/`calculate_size`/`Kelly` reference exists anywhere in `engine.py` — verified by a full-file grep): every backtested trade is sized as a **flat fixed fraction of current capital** —

`BacktestRequest` (the API model in `routes.py`) has **no `position_size_pct` field at all**, so this default of 10% is what every backtest run actually uses, for every symbol/strategy/period, unconditionally — it is not exposed to or configurable by the frontend.

**Why this matters:** position size is a first-order driver of every reported metric — total return, Sharpe/Sortino, max drawdown, VaR/CVaR, and the Monte Carlo p5/p50/p95 band all scale with it. ### Verified correct (independently re-derived, not just read)

- **No same-bar signal+execution lookahead.** Traced `pending_signal`'s full lifecycle: it's set at the *end* of bar `i`'s loop body using bar `i`'s close-based committee decision (`engine.py:813-815`), consumed and reset at the *start* of the very next iteration (bar `i+1`) to execute at bar `i+1`'s **open** price (`engine.py:546-593`). This is the causally correct sequence — a signal can only affect a trade on the next bar, never the same bar it was computed from.
- **RL walk-forward leakage guard is conservative, and correctly so.** `rl_train_cutoff = int(n_rows * 0.60)` is compared against `i` at **trade-close** time (`engine.py:717`), not entry time — so a trade that opens inside the 60% train window but doesn't close until after it is correctly excluded from RL weight updates, rather than leaking a partially-out-of-sample outcome back into training.
- **Indicator formulas in the backtester match the live feed exactly**, including ADX/DI+/DI− (not previously checked in this audit): `dm_p`/`dm_m` directional-movement clipping correctly compares against a *saved copy* of the pre-zeroed `dm_p` (`dm_p_orig`) before zeroing `dm_m`, avoiding the common bug of comparing against an already-modified series — Wilder-smoothed via `ewm(alpha=1/14)` consistently for TR, DI+, DI−, and the final ADX, matching RSI/MACD/ATR's smoothing method.
- **Monte Carlo confidence band** (`_monte_carlo()`, 200-path bootstrap of realized trade PnLs) is methodologically sound as a trade-*ordering*-uncertainty estimate — it resamples actual realized trade outcomes with replacement rather than simulating new ones, so it cannot introduce new look-ahead or fabricate edge that wasn't in the underlying trades.

**Half-Kelly formula and the live Monte Carlo EV gate — independently hand-derived in a follow-up pass, not just read:**

- **Half-Kelly** (`risk/position_sizing.py`): `f* = (p·b − q)/b`, halved. Verified against the standard Kelly criterion with a worked example: p=0.6, b=2.0 → f* = (0.6·2 − 0.4)/2 = 0.4, half-Kelly = 0.2 — matches the textbook formula exactly. `b` is correctly the realized avg_win/avg_loss ratio (Kelly's required reward-to-risk odds, not a hardcoded target), and the negative-edge gate correctly returns 0 shares rather than letting `min(negative, max_cap)` silently produce a negative position size (the exact bug the "Kelly negative edge fix" in the repo's own recent commit history refers to).
- **Monte Carlo EV gate** (`analytics/simulator.py::_calibrate_drift_asymmetric`): solves for the GBM drift θ such that the model's first-passage win probability matches the engine's realized win rate, for the *actual* asymmetric TP/SL barrier distances (not the old symmetric zero-drift approximation, which the code's own comments say made the gate veto nearly every trade). Independently re-derived this from first principles via the martingale optional-stopping theorem: for Brownian motion with drift ν and variance σ², `M_t = e^{-θX_t}` is a martingale exactly when θ = 2ν/σ² (matching the code's `theta = 2*nu/sigma2`); applying optional stopping at the first barrier hit and solving `E[M_T] = 1` for `P(win first)` yields `(e^{θl} − 1)/(e^{θl} − e^{−θw})` — **identical to the code's formula**, not just structurally similar. Cross-checked the θ→0 limit reduces correctly to the classic driftless result `l/(w+l)`, and that P(win) is monotonically increasing in θ in both directions (θ→+∞ gives P→1, θ→−∞ gives P→0), consistent with the code's bisection search assumption. The GBM Itō drift adjustment (`mu = nu + σ²/2`) is also correct. This is genuinely rigorous, correctly-implemented quantitative finance code — a real positive finding, not just "no bug found because I didn't look hard."

Not independently verified: whether the 20-day/1-step-per-day simulation horizon is empirically well-matched to how long real positions with 1.5/2.5 ATR barriers actually take to resolve (the backtester tracks `avg_hold_bars`/`max_hold_bars` for exactly this, but I didn't cross-reference it against the simulator's horizon assumption).

### 20. [MEDIUM, FIXED] `closed_trades` grows unbounded — and the load-bearing dependency on it made a naive fix actively dangerous

**File:** [backend/execution/smart_execution.py](backend/execution/smart_execution.py), [backend/api/routes.py](backend/api/routes.py)

`self.closed_trades` (every historical trade a `SmartExecutionEngine` has ever closed, for the life of the deployment — persisted to and reloaded from `portfolio_state*.json` across restarts) was never capped. Compare `execution_logs`, which is explicitly sliced to the most recent 500 entries before every save (`self.execution_logs[-500:]`) — the same discipline was never applied to `closed_trades`. `_save_state_json()` re-serializes the **entire** list to JSON and rewrites it to disk on every single trade close; for a system explicitly designed for 24/7 autonomous multi-asset trading across 5 markets, this list — and the cost of rewriting it — grew without bound for as long as the deployment ran, undiscounted by a thread offload (unlike the DB save), landing directly on the event loop.

**Why this wasn't a safe one-line fix, and what was actually done:** confirmed via grep that `execution_engine.closed_trades` was read directly, in full, to compute **lifetime** aggregates in all 5 markets' `/portfolio/money-tracker` endpoints (`total_pnl`/`gross_profit`/`gross_loss`/`win_rate`/`total_trades`) — the numbers shown on the Money Tracker page, independently confirmed correct and real earlier in this audit. Simply capping the list the way `execution_logs` is capped — the obvious-looking fix — would have silently made those lifetime totals **wrong** once the cap was reached, only reflecting the most recent N trades.

The fix implemented: `SmartExecutionEngine` now maintains `lifetime_stats` (`total_trades`, `winning_trades`, `total_pnl`, `gross_profit`, `gross_loss`) as O(1) running counters, updated incrementally in a new single choke point, `_record_closed_trade()`, which replaced all 4 previously-separate `self.closed_trades.append({...})` call sites (`force_close()`, `partial_close()`, the COVER branch and the SELL branch of `execute_trade()`). `closed_trades` itself is now capped to the most recent 2000 entries (`_MAX_CLOSED_TRADES`) *after* `lifetime_stats` is updated, so no trade's contribution to the lifetime totals is lost when it ages out of the detail list. `lifetime_stats` is persisted alongside `closed_trades` in both the JSON and DB save/load paths; a `_backfill_lifetime_stats_if_needed()` method reconstructs it once, on load, for any pre-fix state file that doesn't have it yet (run *after* `_sanitize_cross_market()` so trades dropped by cross-market cleanup aren't counted into the backfilled totals). All 5 markets' `/portfolio/money-tracker` endpoints in `routes.py` now read `execution_engine_X.lifetime_stats` instead of re-summing `closed_trades`.

The other `closed_trades`-reading call sites in `routes.py` (equity-curve/performance metrics on `/portfolio/risk`, `/analytics/performance-breakdown`, and the attribution/diagnosis-report endpoints) were reviewed and left as-is: they legitimately need the actual trade *sequence* for equity-curve and per-trade analysis, not a scalar lifetime total, so operating on the bounded 2000-entry list is the correct behavior there, not a bug — Sharpe/drawdown/attribution are properties of recent performance, not lifetime aggregates.

Verified with a new regression test, [backend/tests/test_lifetime_stats.py](backend/tests/test_lifetime_stats.py): incremental accumulation, that `closed_trades` is capped while `lifetime_stats` is not, that `lifetime_stats` stays correct even after trades age out of the capped list (the exact bug a naive fix would have introduced), and that backfill correctly and idempotently reconstructs `lifetime_stats` from a pre-fix state file. Full suite re-run after the change — see Test Results.
